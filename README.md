# Metrix — сверка выручки

Одностраничная админка на Nuxt 4, Vue 3 и TypeScript. Структура повторяет подход cityhelp-diploma: `app/pages`, `app/layouts`, `app/components/Ui`, `app/composables`, `app/utils`, `app/assets`, `server/api`, `server/utils`. Расчеты и контракты находятся в `shared`.

## Запуск

```bash
npm install
npm run dev
```

Открыть http://localhost:3000. При первом открытии показан **демонстрационный отчет**. Для работы с API отключите переключатель «Демо» и подключите оба сервиса. Пароли вводятся в модальных окнах и не записываются в файлы, браузерное хранилище или журналы приложения.

```bash
npm test
npm run typecheck
npm run build
npm start
```

## Как работает сверка

1. Сервер авторизуется в Metrix и Webkassa. Токены хранятся в памяти процесса до 8 часов. Браузер получает только случайный идентификатор HttpOnly/SameSite=Strict cookie. В production необходим HTTPS.
2. Список торговых центров и арендаторов загружается из Metrix. Арендатор опционален. Изменение родительского фильтра сбрасывает выбранные кассы. ЗНК загружаются через `statistic_tenant` для выбранного периода.
3. При выборе всех касс используется `statistic_hourly.daily_totals[].main_count`, в том числе внутри `data`/`Data`. Если итогов нет, суммируются записи `data_hours` по датам. Для отсутствующих или неполных дней выполняется резервный запрос `statistic_tenant` на каждый день с учетом выбранных ЗНК. При выборе части касс выполняется `statistic_tenant` на каждый день: суммируются `main_total` только выбранных ЗНК. Отсутствие кассы в ответе считается отсутствием данных, а не нулевой выручкой.
4. Webkassa: `Shift/ExternalHistory` → все страницы смен → `v4/Ticket/ExternalHistory` → все страницы чеков. Размер страницы 50. Повторные чеки исключаются по кассе, смене и номеру. Дата определяется по `RegistratedOn`, без преобразования времени, как локальная дата Алматы. Для переходящих через полночь смен запрос начинается за день до периода. Это предполагает смены не длиннее 24 часов; семантику отбора открытых смен нужно проверить на реальном API.
5. Расчет «Продажи − возвраты»: OperationType=2 со знаком плюс, OperationType=3 со знаком минус. OperationType=0/1 (покупка/возврат покупки) не входят в выручку продаж. Неизвестный тип блокирует итог Webkassa. Metrix передает готовые суммы с вычтенными возвратами (подтверждено заказчиком). Сверка всегда использует нетто-выручку обоих источников.
6. Деньги хранятся в целых тиынах. Разница = Webkassa − Metrix. Процент = разница / abs(Metrix) × 100. При Metrix=0 и ненулевой разнице процент не определен (тире), при обоих нулях — 0%.
7. Ошибка Webkassa делает его итог по всему периоду неизвестным, чтобы частичная загрузка не выглядела полной. Отчет явно показывает неполноту. Измененные фильтры блокируют экспорт до повторного запуска.

## Выгрузка

- **Excel**: настоящий `.xlsx`, числовые ячейки, итоги, автофильтр, замороженная шапка, выделение расхождений, параметры выборки и пометка деморежима.
- **PDF**: кнопка открывает системный Vдиалог печати. Выберите «Сохранить как PDF». Печатная версия содержит все дни независимо от текущего поиска/вкладки. Ориентация A4 landscape, без навигации. DOCX не реализован; требуемая выгрузка доступна в Excel и PDF.

## Конфигурация и ограничения

- Скопируйте `.env.example` в `.env` и задайте обязательный `NUXT_WEBKASSA_API_KEY`. Он передается сервером в `x-api-key` при авторизации, получении смен и чеков. `npm start` загружает `.env` для production-сборки; после изменения ключа перезапустите сервер.
- `NUXT_WEBKASSA_BASE` и `NUXT_METRIX_BASE` позволяют настроить адреса серверов. Клиент не может задавать произвольный upstream URL.
- Ограничения одного отчета: 31 день, 30 касс; до 100 000 записей в одном пагинированном наборе. При больших объемах нужны фоновые задания с очередью и отдельным хранилищем результатов.
- Сессии находятся в памяти одного Node-процесса и теряются при рестарте. Для нескольких экземпляров потребуется общее защищенное хранилище сессий. Сохраненного архива отчетов и отдельных учетных записей администраторов пока нет.
- В примерах каталогов используется `perPage=10000`. Для каталогов крупнее этого значения потребуется согласовать пагинацию Metrix; ее полный контракт не предоставлен.
- Реальные интеграции нельзя проверить без учетных данных. Реализация основана на переданных контрактах API. Требуется проверка прав аккаунта, схемы токена Metrix и доступности Webkassa ExternalHistory по вашему тарифу.
- Деморежим всегда помечен в интерфейсе и выгрузке. Тестовые суммы не являются финансовыми данными.

## Проверки

`npm test` проверяет денежные суммы, границы периода, знак расхождения, деление на ноль, отсутствие данных, учет возвратов и пагинацию.

`npm run test:integration` после сборки запускает временный сервер с имитацией API: авторизация, каталоги, сопоставимость выбранных касс, 80 чеков, ошибки загрузки, CSRF и отключение сессий.

`npm run test:browser` после сборки запускает отдельный временный сервер и использует установленный Google Chrome: проверяет таблицу, фильтры, скачанный XLSX, блокировку устаревшего отчета, PDF и мобильную ширину. Снимки сохраняются в `/tmp/metrix-desktop.png` и `/tmp/metrix-mobile.png`.

Если предыдущая установка была прервана, выполните `npm ci` для восстановления `node_modules` по lock-файлу. Сообщения `npm warn deprecated` не останавливают установку. В `.npmrc` включено использование кэша и отключен автоматический сетевой аудит во время установки; аудит запускается отдельно командой `npm audit`. Это позволяет установке завершаться независимо от доступности сервиса проверки зависимостей.
